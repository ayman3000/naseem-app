Benchmarks

Same model, same tasks, hidden tests: Naseem is on par with Claude Code and Hermes on speed and tokens. Here is the whole picture, including the run it lost.

Setup

Six coding tasks, each a small real repository with a user-style request and hidden tests. All three harnesses used the same model, kimi-k2.6:cloud through Ollama. Naseem 1.14.0 ran at Medium reasoning; Claude Code and Hermes ran from the command line at their defaults. Time is each harness's own run time; tokens are input tokens including cache reads. Sep 29–30, 2026.

What it shows

On par, not ahead

On tasks it was tuned for, Naseem is fastest on three of five and sends the fewest tokens on four. On the fresh task it sits between the two CLIs on time and tokens and dropped one run of two. A week before these runs it was about twice as slow as both CLIs; that gap is gone.

Correctness comes from checking

The failures on both sides came from the model taking a shortcut, such as editing tests to make them pass, or guessing an unstated format. The harness that checks the work against the request catches the first kind; nothing catches the second every time.

The remaining gap is call count

On the hard tasks Naseem makes more model calls (27 on t11 against 22 and 13). Each is short, so time stays close, but fewer, better-planned calls would cut time and cost. That is the next thing to fix.

Limitations

  • One run per task on the five, two on the sixth: differences under about 20% are noise.
  • Naseem's author wrote the tasks and the benchmark, and Naseem was developed against five of the six.
  • One model only. Claude Code is built around Claude models and ran a third-party model here; every harness may do better on its own.
  • Settings differ slightly: Naseem at Medium reasoning, the CLIs at their defaults; Claude Code ran with a scoped tool permission list.

Raw run logs, hidden-test output and per-run metrics are kept with the benchmark. Ask on the community forum if you want them.
