How it works

The philosophy page says why Naseem behaves the way it does. This one says how. Each section names the mechanism and where you can see it in the app, so every claim here can be tested.

1. Context that stays small

Long tasks die of context bloat: every file read and every build log lands in the prompt until the model forgets the objective. Naseem keeps the whole conversation but replaces each finished tool exchange with a one-line receipt — head and tail of the output, with the full text spilled to an artifact the model can search or re-read on demand. Eviction is budget-driven and sticky: once a result is folded it stays folded, so the prompt prefix stays byte-stable and your provider's prompt cache keeps hitting.

When a run stalls — every tool call in a turn failed or repeated an earlier one — Naseem does not keep burning turns. It pauses, posts the objective, the turn budget, and "what I tried", and waits. Your next message resumes exactly where it stopped.

Memory across conversations is markdown on disk: one file per fact plus an index, in Application Support, seeded on first launch. The model reads the index first and opens a fact only when it needs it. Reveal in Finder shows you everything it knows.

See it: the tool trail in any run · the brain icon in the toolbar → Memory → Reveal in Finder.

2. Simulator and Mac, driven natively

iOS Simulator. Lifecycle goes through Apple's own simctl: list, boot, install, launch. For the UI, Naseem builds a small XCTest driver once and runs it inside the Simulator as a loopback-only server. The agent reads an accessibility snapshot and taps elements, never coordinates. Every snapshot carries a generation number; a tap that references an element from an older snapshot is rejected as stale, so the agent cannot act on a screen that has already changed.

Mac apps. Native Accessibility API plus synthetic input events. No AppleScript, no screenshots-and-guess, no embedded browser or cloud VM. Every conversation has its own allowlist of apps; the first time the agent reaches for an app that is not on it, you get an approval sheet, and the approval takes effect on that very call.

See it: tools named sim_ui, sim_tap, mac_ui, mac_click in the trail · the app allowlist in each conversation's settings. Both are Pro.

3. Eyes for any model

Most good coding models are text-only. When a screenshot arrives and the chat model cannot see, Naseem sends the image to the vision model you chose and hands the description back to the chat model as its own inspection. If no vision model is configured, the agent is required to say on the first line of its reply that it could not see the image — no silent guessing. The vision call's tokens are recorded in Usage & Cost like everything else.

See it: Settings → General → Vision model (provider and model) · the "inspected for you by …" block in the trail.

4. Suggestions from your project, not a template

Each project gets a naseem/ folder with three markdown files: project.md (what it is, stack, how to build and test), roadmap.md (done, in progress, next, known issues) and journal.md (one dated line per run). Every project chat reads the first two up front. Start cards are generated from the roadmap's "Next" items and the folder itself, cached for a day, refreshed in the background.

Generation runs on a helper model, not your chat model: a reasoning model once spent thirty seconds and its whole token budget thinking about six one-line cards. If you don't pick one, Naseem chooses a fast, cheap sibling from the same provider.

See it: naseem/ in any project folder · Settings → General → Helper model · the start panel of a new chat.

5. Rules that cannot bluff

A rule's conversation is rolling, so every run starts with a stamp declaring earlier observations out of date. A run that ends without a single tool call is refused and sent back to actually look. Quiet rules must end with an explicit ALL CLEAR or ATTENTION marker; a reply with neither is treated as attention, so silence can never mean success. Dry run forbids every writing tool and asks for a description of what would have happened.

Once a week a heartbeat leads with the run count per rule and names any rule that did not run. The menu bar shows the age of the last run, and a rules-status.json in your Outputs folder mirrors it for anything else that wants to watch.

See it: Tools → Rules · the menu-bar badge · Outputs/rules-status.json. Pro, currently Beta.

6. Light by construction

Naseem is Swift and AppKit/SwiftUI end to end. There is no JavaScript runtime, no Chromium, no Python sidecar. Heavy work — the compiler, the Simulator, the model — happens outside the process. The Memory panel reads the same physical-footprint number Activity Monitor shows, plus the session peak, and attributes it to components so you can see what a long session actually costs.

See it: Tools → Usage & Cost → Memory. A measured figure is on the philosophy page.

7. Where your data goes

Naseem hosts nothing. Every connection leaves your Mac directly for a service you configured with your own key.

your Mac ──▶ model provider API (Anthropic, OpenAI, Gemini, OpenRouter, Ollama Cloud) your Mac ──▶ api.telegram.org (long-polled by the app; replies go the same way) your Mac ──▶ Tavily or Brave (web search, only if you add a key) your Mac ──▶ nowhere (local Ollama, on-device MLX) Naseem servers: none. Telemetry: none.

Telegram accepts commands only from the user id you set. The gateway does not start until one is configured: blank means nobody, not everybody.

See it: Settings → Providers · Settings → Integrations → Telegram → Allowed user id.
